## Why there are two engines

The checkpoint represents one cooperative UniV2X system, but inference has two different input contracts and state machines. The infrastructure agent runs first, then selected road-side tracks, map/reference tensors, occupancy features, and transforms are prepared for the ego agent. Exporting one infrastructure engine and one ego engine preserves that sequential contract; they are not duplicate models and are not invoked as a single fused forward.

## Implemented deployment behavior

- Separate infrastructure and ego ONNX export, calibration, profiles, and engines.
- Explicit-QDQ INT8 with global MatMul exclusion.
- Relative per-scene timestamps are formed on the host before float32/FP16 conversion; absolute epoch timestamps around `1.626e9` overflow FP16 and caused the earlier non-finite state.
- Inverse-sigmoid/log chains use finite epsilon/floor rewrites; occupancy `-inf` sentinels use a finite `-10000` invalid value.
- Sensitive `lane_reference`, timestamp/BEV, and MSDA lineages are constrained to FP32 where required by numerical tests.
- Temporal track input is padded to 960 rows with the graph's `-10000` invalid sentinel.
- Cooperative track input is padded to 64 rows with an out-of-range matched index so padding is excluded from fusion.
- One execution context per engine/profile is retained; fixed shapes prevent per-frame Myelin execution-configuration rebuilds.
- Runtime records infrastructure, ego, combined forward, and full end-to-end latency separately.

Divider IoU is explicitly undefined in all four evaluator outputs because this validation result has no valid divider IoU denominator; it is not treated as zero. This evaluator does not emit a separate motion-forecasting headline metric, so no motion score is invented from intermediate tensors.

The same-runtime forward trend is `FP32 315.491 ms > FP16 235.290 ms > INT8 219.240 ms`, matching the expected qualitative precision trend. FP16 is about `1.34x` faster than FP32, INT8 is about `1.44x` faster than FP32, and INT8 is about `1.07x` faster than FP16. End-to-end mean is not monotonic because CPU sample preparation periodically drains the DataLoader prefetch queue; it is not used to infer engine compute scaling.

Accuracy still does not reproduce the PyTorch task baseline. TensorRT FP32 already falls from `mAP 0.051554` to `0.028844`, from `AMOTA 0.109535` to `0.079392`, and from occupancy IoU `22.5408/25.7962` to `13.4097/10.1413`. The main accuracy gap therefore exists in the export/runtime or result-reconstruction contract before reduced-precision quantization. FP16 and INT8 add smaller incremental degradation on top of that FP32 gap.

TensorRT FP32 is the non-quantized backend-conversion baseline, not an FP32 quantization mode. Keeping FP32 arithmetic does not preserve semantics if ONNX export rewrites, custom plugins, output ordering/decoding, host cooperative fusion, or recurrent state updates differ. TF32 was explicitly disabled in these engine builds, so the observed gap is not explained by TF32 or calibration. On the first ego frame, planning is allclose (`max abs 0.001831`) and occupancy sigmoid is allclose (`max abs 7.7e-6`), but detection labels already have 29 mismatches, drivable segmentation has 427 mismatched pixels, lane-class logits have max/mean absolute errors `2.0673/0.05975`, and `lane_reference` has `1.2623/0.04131`. Those task-head differences are then propagated by tracking and cooperative temporal state over 675 frames. The exact first divergent layer or host reconstruction step is not yet isolated, so FP32 fidelity remains a blocking defect rather than an accepted accuracy result. The concise source-hash audit is retained at `UniV2X/evidence/fp32_export_parity/frame0_summary.json`.

## Data-loader latency finding

After excluding 20 warmup frames, FP16 data wait was p50 `0.235 ms`, mean `1588.289 ms`, and p99 `8138.408 ms`. Of 655 measured frames, 187 exceeded 1 s and 142 exceeded 5 s. Storage sampling showed zero I/O wait and low disk utilization; the four DataLoader workers used for these completed runs were CPU-bound preparing cooperative samples, and the fast engine periodically drained their prefetch queue. Pure forward latency is therefore reported separately from end-to-end latency.

The PyTorch and TensorRT evaluation entry points now default to eight DataLoader workers, matching `workers_per_gpu=8` in the model configuration. This does not retroactively change the table above: those retained 675-frame latency artifacts were measured with four workers. A same-host, same-load rerun is required before attributing any end-to-end change to the new worker count; increasing workers can reduce queue starvation but can also increase CPU contention under concurrent training.
