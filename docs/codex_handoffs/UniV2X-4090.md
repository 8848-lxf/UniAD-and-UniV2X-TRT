## Why there are two engines

The checkpoint represents one cooperative UniV2X system, but inference has two different input contracts and state machines. The infrastructure agent runs first, then selected road-side tracks, map/reference tensors, occupancy features, and transforms are prepared for the ego agent. Exporting one infrastructure engine and one ego engine preserves that sequential contract; they are not duplicate models and are not invoked as a single fused forward.

## Implemented deployment behavior

- Separate infrastructure and ego ONNX export, calibration, profiles, and engines.
- Explicit-QDQ INT8 with global MatMul exclusion.
- Relative per-scene timestamps are formed on the host before float32/FP16 conversion; absolute epoch timestamps around `1.626e9` overflow FP16 and caused the earlier non-finite state.
- Inverse-sigmoid/log chains use finite epsilon/floor rewrites; occupancy `-inf` sentinels use a finite `-10000` invalid value.
- Sensitive `lane_reference`, timestamp/BEV, and MSDA lineages are constrained to FP32 where required by numerical tests.
- Temporal track input is padded to 960 rows with the graph's `-10000` invalid sentinel.
- Cooperative track input is padded to 64 rows with an out-of-range matched index so padding is excluded from fusion.
- One execution context per engine/profile is retained; fixed shapes prevent per-frame Myelin execution-configuration rebuilds.
- Runtime records infrastructure, ego, combined forward, and full end-to-end latency separately.

## Data-loader latency finding

After excluding 20 warmup frames, FP16 data wait was p50 `0.235 ms`, mean `1588.289 ms`, and p99 `8138.408 ms`. Of 655 measured frames, 187 exceeded 1 s and 142 exceeded 5 s. Storage sampling showed zero I/O wait and low disk utilization; the four DataLoader workers were CPU-bound preparing cooperative samples, and the fast engine periodically drained their prefetch queue. Pure forward latency is therefore reported separately from end-to-end latency.
